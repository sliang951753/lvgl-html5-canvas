# lvgl-html5-canvas wire protocol (v0)

Binary, little-endian, framed over a single WebSocket binary message per
frame. Subprotocol: `lhc-v0`.

This is the **single source of truth** for the wire format. The C
encoder (`src/proto/encoder.c`) and the JS decoder
(`web/decoder.js` — generated by `scripts/gen_js_protocol.py` from
`src/proto/protocol.h`) both follow this document.

---

## 1. Message layout

Every WS binary message represents exactly one frame:

```
+---------------------+
|   frame header (4)  |
+---------------------+
|   command 0         |
+---------------------+
|   command 1         |
+---------------------+
|   ...               |
+---------------------+
|   command N-1       |
+---------------------+
```

### Frame header (4 bytes)

| Offset | Size | Field       | Notes                                  |
|-------:|-----:|-------------|----------------------------------------|
| 0      | 2    | `frame_id`  | u16 LE, monotonically increasing       |
| 2      | 2    | `cmd_count` | u16 LE, number of commands that follow |

`frame_id` wraps at 65535 — viewers must accept wrap.

### Command (variable)

```
+----+----+----+----+--------- payload (payload_len bytes) ---------+
| op | fl |  payload_len  |                                         |
+----+----+----+----+-----------------------------------------------+
```

| Offset | Size | Field         |
|-------:|-----:|---------------|
| 0      | 1    | `opcode`      |
| 1      | 1    | `flags`       |
| 2      | 2    | `payload_len` (u16 LE) |
| 4      | `payload_len` | payload bytes |

Decoders MUST skip unknown opcodes by advancing `4 + payload_len` bytes.

## 2. Opcodes (v0 / M3a)

| Opcode | Name          | Direction | Payload |
|-------:|---------------|-----------|---------|
| 0x01   | BEGIN_FRAME   | S → V     | 4 bytes: `u16 w, u16 h` |
| 0x02   | END_FRAME     | S → V     | 0 bytes |
| 0x10   | FILL_RECT     | S → V     | 13 bytes |
| 0x11   | BORDER        | S → V     | 15 bytes |
| 0x12   | LINE          | S → V     | 13 bytes (`i16 x1,y1,x2,y2; u32 argb; u8 width`) |
| 0x13   | BOX_SHADOW    | S → V     | 20 bytes |
| 0x21   | IMAGE         | S → V     | 12 bytes |
| 0x40   | BLOB_UPLOAD   | S → V     | variable (`9 + data_len`) |
| 0x41   | BLOB_EVICT    | S → V     | 4 bytes |

Every frame **must** start with BEGIN_FRAME and end with END_FRAME.
Unknown future opcodes must still be skipped via `payload_len`.

> Note (M2d): `LV_DRAW_TASK_TYPE_LAYER` currently reuses the IMAGE/blob path
> and is therefore emitted on-wire as `BLOB_UPLOAD + IMAGE` (no dedicated
> `OP_LAYER` yet).

### FILL_RECT payload (13 bytes)

| Offset | Size | Field   | Notes                                |
|-------:|-----:|---------|--------------------------------------|
| 0      | 2    | `x`     | i16 LE, top-left in canvas pixels    |
| 2      | 2    | `y`     | i16 LE                               |
| 4      | 2    | `w`     | i16 LE, width  in pixels             |
| 6      | 2    | `h`     | i16 LE, height in pixels             |
| 8      | 4    | `argb`  | u32 LE bytes = `[B, G, R, A]`        |
| 12     | 1    | `radius`| u8, corner radius in pixels (0 = sharp) |

Flag bit 0 (`HAS_ALPHA_HINT`) is set when `A != 0xFF`, letting the
decoder skip a blend setup. It is purely advisory.

#### Colour byte order — critical

The C source writes
`argb = (A << 24) | (R << 16) | (G << 8) | B`
as a u32 LE → on the wire the bytes are `[B, G, R, A]`.

- JS: read with `view.getUint32(off, /*little=*/true)`, then mask out
  R/G/B/A and feed into `ctx.fillStyle = "rgba(r,g,b,a)"`.
- Python (`ws_capture.py`): unpack with `struct.unpack("<BBBB", …)` →
  `b, g, r, a`.

This was a real bug source during M1; the e2e test now pins it.

### LINE payload (13 bytes)

| Offset | Size | Field   | Notes |
|-------:|-----:|---------|-------|
| 0      | 2    | `x1`    | i16 LE, start point x |
| 2      | 2    | `y1`    | i16 LE, start point y |
| 4      | 2    | `x2`    | i16 LE, end point x |
| 6      | 2    | `y2`    | i16 LE, end point y |
| 8      | 4    | `argb`  | u32 LE bytes = `[B, G, R, A]` |
| 12     | 1    | `width` | u8, line width in px |

Current M3a server emits LINE only for simple single-segment line tasks
(no polyline array, no dash, no round caps). Unsupported line styles
fall back to LVGL SW draw unit.

## 3. Frame semantics

- The server is authoritative. A new viewer that connects mid-stream
  sees the next BEGIN_FRAME and is up to date one cycle later (FULL
  refresh mode in M1).
- **The server skips empty frames.** LVGL's internal refresh timer
  fires a no-op refresh ~30 ms after every forced full repaint; if it
  were broadcast it would carry `BEGIN_FRAME, END_FRAME` only (zero
  fills) and the viewer would blank to black between real frames. The
  draw unit therefore drops any frame with 0 FILL_RECTs. Regression
  test: `tests/test_protocol_e2e.py`.
- Each frame is one WS binary message. No fragmentation across
  messages. A frame whose encoded size exceeds the server-side buffer
  (M1: 64 KiB) is dropped with a stderr log.
- Per-viewer ring buffer is 16 frames; slow viewers get drop-oldest, not
  back-pressure.

---

## 4. Versioning

`protocol.h` defines `LHC_PROTOCOL_VERSION` (currently `0`). When the
wire format changes in an incompatible way, bump the major and change
the WS subprotocol string (`lhc-v0` → `lhc-v1`). Optional opcodes
(e.g. new draw ops) can be added without bumping as long as decoders
respect the skip-unknown rule above.
